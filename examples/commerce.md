# Shared commerce persistence

Apply `sql/0.0.6_events.sql`, then `sql/0.0.7_commerce.sql` explicitly. The latter
is optional and compatible with the 0.0.6 browser runtime. No migrations run on import.

Use seven shared tables for all products, keyed by `product_name`. The commerce
extension adds checkout attempts, webhook receipts and pending payment observations;
the existing Stripe customer table handles both guests and accounts. It contains
no product-specific plans, Clerk configuration or Payment Links.

Trusted endpoints choose a constant product name, validate GrowthKit envelopes,
verify authentication and disregard client-supplied account/product IDs. Only
server credentials can access commerce tables and RPCs. Supabase `service_role`
access spans products, so these scopes are not separate security tenants.

## RPC contracts

- `growthkit_identify(p_product_name, p_visitor_id, p_user_id)` links a visitor to
  the session-verified account and attaches earlier guest checkout/customer mappings.
  Conflicting account links fail atomically. Use this instead of the base
  `growthkit_link_identity` when commerce linking is required.
- `growthkit_checkout(p_product_name, p_event, p_plan)` persists the validated
  `checkout_started` envelope and attempt atomically. The attempt ID is the event
  UUID generated by GrowthKit. Retries use that same ID. The backend checks plan
  availability and returns the configured checkout URL with a signed reference.
- `growthkit_process_webhook(p_product_name, p_provider, p_event_id, p_events,
  p_attempt_id = null, p_session_id = null, p_customer_id = null)` commits the receipt,
  optional Stripe association, authoritative events and pending-payment cleanup
  atomically. Failed processing consumes no receipt; duplicate provider events return
  without recording revenue again. Event product names must match the trusted scope.
  Logical invoice/checkout deduplication uses base event `source_event_id`.

Commerce mutations take a transaction advisory lock per product to prevent late
signup and webhook linking from racing. This intentionally serializes these short
mutations within a product; ordinary event ingestion does not take that lock.

## Application responsibilities

1. Verify raw webhook signatures and production mode before database access.
2. Bind only verified purchases to stored, signed checkout references. Include product
   name in the signature. Never authorize access based on visitor IDs or references.
3. Resolve Stripe customer mappings using both `product_name` and `stripe_customer_id`.
   Guests have a visitor ID and nullable `user_id`. Do not match purchases by email.
4. If a signed financial observation has no recoverable association, upsert it into
   `growthkit_pending_payments` with `product_name`, `provider`, `source_event_id`,
   `webhook_event_id`, optional `stripe_customer_id`, and its validated event JSON.
   Conflict target: `(product_name,provider,source_event_id)`. Event product and source
   must match those columns. Keep associations null; do not invent user/visitor IDs.
   Return a retryable response. Successful webhook processing removes matching pending
   observations within the same product/provider; reports must include pending rows
   as explicitly unknown revenue. Monitor and replay after the provider retry window.
5. Distinguish initial recurring MRR, recurring cash and lifetime cash. Lifetime MRR
   is zero. Cancellation requests and effective end are separate observations.

The SDK deliberately supplies no Stripe, Clerk or Supabase runtime dependencies.
Each product retains its verified authentication, billing rules and event definitions.
The shared SQL provides storage/deduplication; it does not calculate invoice amounts,
validate payment signatures, configure provider webhooks, or grant entitlements.
